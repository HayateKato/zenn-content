このワークショップで実際のシステムに近いのアーキテクチャを考えることで、クラウドサービスへの理解を深めたり現役エンジニアと同じような実務の視点でインフラを考えたりする経験を積めると思い、参加しました。

## ワークショップの概要と流れ

題材は「複数ファンクラブサイトを統合的にホスティングするプラットフォームの設計」でした。
各ファンクラブサイトは独立したテナントとして管理しますが、定期的に新サイトが追加されるという技術要件があり、マルチテナント環境を想定してサービスの疎結合性や拡張性を担保したアーキテクチャを考える必要がありました。
他にも、ファンクラブサイトならではの突発的なアクセスへの対応や、コストの最適化、技術組織の規模など、さまざまな要件がありました。
（後から聞いた話ですが、とても抽象的な課題設定であり、現役エンジニアの間でもさまざまなアーキテクチャ案が生まれるようでした。）

題材に対して、チーム内の他の学生と相談したりメンターの方々からアドバイスを頂いたりしながら、個人でアーキテクチャーを考えていきました。
個人ワーク終了後は、各チームごとに自身が設計したアーキテクチャを発表し、それに対して質問やフィードバックを受けました。

いざ、アーキテクチャの設計に取り組んだわけですが、私自身AWSはEC2やVPC, S3といった基本的なサービスに触れたことしかなく、1からアーキテクチャを考える際に何から手をつけて良いのかが分かりませんでした。
そこで、まずはネット上に転がっている同じような題材を扱ったアーキテクチャーがないかを探しました。
すると、去年のArchitecture Challengeに参加された方の記事を見つけました。

https://qiita.com/yukkun/items/7d4045af17fd38905039

これを土台として、記事の中で触れられていたマルチテナント管理に対するフィードバックや、私自身が感じたチケット購入時の負荷に関する課題を解決できるよう、変更を加える方針で作業を行いました。

## 作成したアーキテクチャと構成の理由

以下が作成したアーキテクチャになります。
主に、可用性とコスト効率に焦点を当ててアーキテクチャーを考えました。

![](/images/431c7afb477055/architecture.png)

### EKS × Karpenterによるスケーリング

参考にした記事では、サイトごとにEC2を割り当てていました。
しかし、これだと1人のエンジニアが複数サイトを保守するような状況では負担がかかり、運用しやすいとは言えません。
（今回の要件では、プラットフォーム運用に割ける人員は3, 4人程度でした。）
また、EC2ごとにスケーリングするため、各サイトが個別に最低1台のインスタンスを常時持つ必要があり、トラフィックの少ないサイトでも遊休リソースを抱えてしまいます。
さらに、スケールアウト時に新しいインスタンスが起動して実際にトラフィックを受けられるまでには時間がかかります。
これらの問題点を解決するため、複数のサービスについて調査し、比較検討を行いました。

**ECS**
- AWS独自のコンテナオーケストレーションサービス。
- Kubernetesの知識がなくても使えるため、学習コストが比較的低い。
- ただし、Namespaceによるマルチテナント分離など、Kubernetes固有の機能は使えない。

**EKS**
- KubernetesをAWSで管理するマネージドサービス。
- Namespaceによるテナント分離やHPA（Horizontal Pod Autoscaler）など、Kubernetesエコシステムをフル活用できる。

**ECS vs EKS**
各サイトごとにNamespaceで分離し、リソースの割り当てをテナント単位で制御したいため、EKSを選択しました。

**Cluster Autoscaler × Auto Scaling Group**
- ノードスケーリングをAuto Scaling Groupと連携して行う従来の方法。
- スケールアウト時にAuto Scaling Groupを経由するため、新ノードが起動してPodを受け付けるまでに数分かかることがある。

**Karpenter**
- AWSが主導するOSSのノードオートスケーラー。
- Auto Scaling Groupを経由することなく、高速にEC2を増やせる。
- Podのリソース要求に合わせて最適なインスタンスタイプを自動選択するため、コスト効率も高い。

**Fargate**
- ノード管理が不要なサーバーレスコンテナ実行環境。
- ただし、EC2ベースと比較して単価が割高になりやすく、常時稼働するWorkloadには不向き。



**Cluster Autoscaler × Auto Scaling Group vs Karpenter**
すぐにノードを起動でき、突発的なアクセス増にも対応しやすいため、Karpenterを選択しました。

### Namespace分離によるノイジーネイバー対策

特定のテナントへの負荷が増大した際、そのテナントへのリソース割り当てが増えた分だけ、他のテナントのリソースが圧迫されてしまいます（ノイジーネイバー問題）。
これに対して、共通機能・サイトごとにNamespaceに分離することで、部分的に各テナント専用のリソースを決めておくことができます。
上記の「トラフィックの少ないサイトでも遊休リソースを抱えてしまう」という問題と矛盾するかもしれませんが、ここは運用を通じて調整する必要がありそうです。

### マルチAZ構成によるDBの可用性担保

参考記事では、DB（Aurora： リレーショナルDB）をMaster & Slaveによるフェイルオーバー構成にしていました。
しかし、これでは同一AZ内で地震等の物理的障害が起きた際、MasterとSlaveどちらのDBも影響を受けてしまう可能性があります。
そこで、マルチAZ（Availability Zone：リージョン内にある物理的に分離されたデータセンターの集合）構成を採用することで、東京リージョン内の異なるAZ間でDBを冗長化し、一方のAZで障害が発生してもデータが失われないようにしました。

### RDSリードレプリカによるDBへのアクセス負荷分散

今回の要件では、ファンクラブサイトでのチケット販売システムも含まれていました。
具体的には、サイト内で会員ランク（有料会員 or 無料会員）に応じて外部チケット販売サイトへのリンクを提供するという内容でした。
私自身も経験がありますが、チケット先行ではたくさんの人がシステムに一度にアクセスします。
今回、DBに以下のような情報が入っていると仮定し、チケット先行アクセス時にDBから会員ランクを取得し、遷移先リンクを決めるという処理をLambdaで動かす仕組みにしました。
そのため、チケット先行時にDBに高負荷がかかることが予測されます。

| カラム名 | 説明 |
|---|---|
| id | |
| cognito_sub | Cognitoの認証ID |
| fanclub_id | どのファンクラブか |
| status | 会員状態 |
| member_rank | 会員ランク |
| started_at | 有料会員の開始日時 |
| expires_at | 有料会員の終了日時 |

最初はRedisのようなメモリDBを用意してキャッシュとし、そこから会員ランクを取得することで負荷軽減を行おうとしていました。
しかし、キャッシュ情報がきちんと更新されていないと、例えば有料会員なのに無料会員のページに遷移してしまうなど、お金が絡んだ問題になってしまいます。
メンターの方にこの問題を相談したところ、以下のようなアドバイスを頂きました。

- キャッシュ情報の精度を担保するのはアプリ（実際のファンクラブサイトにおける処理）が絡む要件であるため、SRE側だけでは決めかねる。
- チケット購入時のDBへの問い合わせは読み取りだけでよく、そういう時はRDSリードレプリカを使うといい。

RDSリードレプリカは読み取り専用のDBコピーであり、プライマリDBのデータが書き換わると、キャッシュと違ってプロバイダ（今回だとAWS）が非同期で複製されたDBの更新を行ってくれます。
RDSリードレプリカはAWSが更新を管理するため、アプリ側でキャッシュ無効化ロジックを実装する必要がありません。

## 振り返り

### できなかったこと

今回は時間が足りず、セキュリティや監視、開発環境についてまでは考えられませんでした。
もし時間があれば、以下の構成でアーキテクチャを更新しようと考えています。

**セキュリティ**
- AWS WAF：SQLインジェクションやクロスサイトスクリプティング対策。
- AWS Shield：DDoS対策。

**監視**
- Prometheus × Grafana：コンテナ環境と相性がいい。

**開発環境**
- Terraform：AWSサービスをモジュール化し、IaC管理できる。
- ArgoCD：コンテナをGitOpsで管理できる。

### 学んだこと

メンターからのフィードバックを通じて、DBの読み書きを目的ごとにエンドポイントで分けるという手法を学びました。
無料会員から有料会員への変更（書き込み）はプライマリDBで行い、会員ランクの参照（読み取り）はリードレプリカに向けるといった使い分けです。
これにより、プライマリDBへの負荷を分散しつつ、チケット先行のような高トラフィック時でも安定した参照を実現できます。

また、AWSやGoogle Cloudを単独で使うのではなく、複数のクラウドサービスを組み合わせた方が性能やコストで有利になるケースもあると教わりました。
例えば、CloudFrontの代わりにCloudflareのCDNを活用するなど、特定のドメインに強いプロバイダを使うといった感じです。

さらに、他の学生の発表では、「このサービスを使うと速い・安い」と述べるだけでなく、具体的に何秒・いくら改善されるかを数値で示してアーキテクチャを評価している方もいました。
感覚的・抽象的な根拠よりも、定量的な指標に基づく根拠にはとても説得力があり、聞き手への伝わり方が大きく変わると感じました。

加えて、SREの視点では「アプリケーション層で対応するか」、「インフラ層で捌くか」を状況に応じて判断する力が重要だと感じました。
コストやパフォーマンスの観点から、どの層に責任を持たせるかという設計判断は、実際の現場でも問われる場面が多そうです。
