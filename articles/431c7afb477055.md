## はじめに

2026年6月27日にCyberAgentの1dayワークショップの「**Architecture Challenge**」に参加してきました！

[Architecture Challenge](https://www.cyberagent.co.jp/careers/students/event/detail/id=33042)とは

> Architecture Challenge ~ 複数のサービスを支えるマルチテナンシーなプラットフォームを設計せよ ~ は、【SRE】【パブリッククラウド】、【プラットフォームエンジニアリング】に興味のあるエンジニアを対象とした1dayの個人参加型インターンシップです。
> 提示されたテーマに基づき、参加者はメンターのサポートを受けながら高度なアーキテクチャ設計に取り組みます。イベントの最後には、課題を提示した社員からフィードバックを受けることができます。
> メンターのサポートを受けながら実践的な課題に取り組み、現場に近い環境で設計経験を積めます。
> システムの信頼性確保やクラウド活用、コスト最適化など、SREやプラットフォームエンジニアが直面する技術的課題に挑戦することで、実務で必要な技術力を磨く絶好の機会となります。

参加した理由としては、私自身研究室のサーバー管理や長期インターンを通じて物理サーバーやAWS等を触る機会はあったのですが、AWSやGoogle Cloudで展開されている各コンポーネントへの理解が浅く、またそれらをどう組み合わせてサービスを開発・運用・拡張していくのかを考える機会がありませんでした。
このワークショップではそのような経験を積めると思い、参加しました。

## ワークショップの概要

題材は「複数ファンクラブサイトを統合的にホスティングするプラットフォームの設計」でした。
マルチテナント環境を想定し、各ファンクラブサイトは独立したテナントとして管理し、定期的に新サイトが追加されるという技術要件がありました。
そのため、サービスの疎結合性や拡張性を担保したアーキテクチャを考える必要がありました。
他にも、ファンクラブサイトならではの突発的なアクセスへの対応や、コストの最適化、技術組織の規模など、さまざまな要件がありました。
（これは後から聞いた話ですが、とても抽象的な課題設定であり、現役エンジニアの方でもさまざまなアーキテクチャ案が生まれるようでした。）

## 当日の流れ

### 出だし

### EKS × Karpenterによるスケーリング

参考にさせていただいた記事では、サイトごとにEC2を割り当てていました。
これだと、1人のエンジニアが複数サイトを保守することがある状況では負担がかかり、運用しやすいとは言えません。（今回の要件では、プラットフォーム運用に割ける人員は3, 4人程度でした。）
また、EC2ごとにスケーリングするため、各サイトが個別に最低1台のインスタンスを常時持つ必要があり、トラフィックの少ないサイトでも遊休リソースを抱えてしまいます。
さらに、スケールアウト時に新しいインスタンスが起動して実際にトラフィックを受けられるまでには時間がかかります。
これらの問題点を解決するため、以下の技術を比較検討しました。

#### ECS
- AWS独自のコンテナオーケストレーションサービス。
- Kubernetesの知識がなくても使えるため、学習コストが比較的低い。
- ただし、Namespaceによるマルチテナント分離など、Kubernetes固有の機能は使えない。

#### EKS
- KubernetesをAWSで管理するマネージドサービス。
- Namespaceによるテナント分離やHPA（Horizontal Pod Autoscaler）など、Kubernetesエコシステムをフル活用できる。

#### Cluster Autoscaler × Auto Scaling Group
- ノードスケーリングをAuto Scaling Groupと連携して行う従来の方法。
- スケールアウト時にAuto Scaling Groupを経由するため、新ノードが起動してPodを受け付けるまでに数分かかることがある。

#### Karpenter
- AWSが主導するOSSのノードオートスケーラー。
- Auto Scaling Groupを経由することなく、高速にEC2を増やせる。
- Podのリソース要求に合わせて最適なインスタンスタイプを自動選択するため、コスト効率も高い。

#### Fargate
- ノード管理が不要なサーバーレスコンテナ実行環境。
- ただし、EC2ベースと比較して単価が割高になりやすく、常時稼働するWorkloadには不向き。

#### ECS vs EKS
各サイトごとにNamespaceで分離し、リソースの割り当てをテナント単位で制御したいため、EKSを選択しました。

#### Cluster Autoscaler × Auto Scaling Group vs Karpenter
すぐにノードを起動でき、突発的なアクセス増にも対応しやすいため、Karpenterを選択しました。

#### Fargate
EC2ベースと比べてコストが高くなるため除外しました。

以上の理由からEKS × Karpenterを選択しました。

### Namespace分離

何も対策しないと、特定のテナントへの負荷が増大した際に、そのテナントへのリソース割り当てが増えた分だけ他のテナントのリソースが圧迫されてしまいます（ノイジーネイバー問題）。
これに対して、共通機能・サイトごとにNamespaceに分離することで、部分的に各テナント専用のリソースを決めておくことができます。
上記の「トラフィックの少ないサイトでも遊休リソースを抱えてしまう」と言う問題と矛盾するかもしれませんが、ここは運用を通じて調整する必要がありそうです。

### マルチAZ構成によるDBの可用性担保

参考記事では、DB（Aurora： リレーショナルDB）をMaster & Slaveによるフェイルオーバー構成にしていました。
しかし、これでは同一AZ内で地震等の物理的障害が起きた際、masterとslaveどちらのDBも影響を受けてしまう可能性があります。
そこで、マルチAZ（Availability Zone：リージョン内にある物理的に分離されたデータセンターの集合）構成を採用することで、東京リージョン（ap-northeast-1）内の異なるAZ間でDBを冗長化し、一方のAZで障害が発生してもデータが失われないようにしました。

### RDSリードレプリカによるDBへのアクセス負荷分散

今回の要件では、ファンクラブサイトでのチケット販売システムも含まれていました。
具体的には、サイト内で会員ランク（有料会員 or 無料会員）に応じて外部チケット販売サイトへのリンクを提供するという内容でした。
> 例：有料会員は先行販売サイトにアクセスできる、無料会員よりも値段が安いなど

私自身も経験がありますが、このチケット先行というのはたくさんの人が一度にアクセスする瞬間であり、高負荷がかかります。
今回、DBに以下のような情報が入っていると仮定し、DBから会員ランクを取得し、遷移リンクを決めるという処理をLambdaで動かす仕組みにしました。

| カラム名 | 説明 |
|---|---|
| id | |
| cognito_sub | Cognitoの認証ID |
| fanclub_id | どのファンクラブか |
| status | 会員状態 |
| member_rank | 会員ランク |
| started_at | 有料会員の開始日時 |
| expires_at | 有料会員の終了日時 |

最初はRedisのようなメモリDBを用意してキャッシュとし、そこから会員ランクを取得することで負荷軽減を行おうとしていました。
しかし、キャッシュ情報がきちんと更新されていないと、例えば有料会員なのに無料会員のページに遷移してしまうなど、お金が絡んだ問題になってしまいます。
メンターの方にこの問題を相談したところ、以下のようなアドバイスを頂きました。

- キャッシュ情報の精度を担保するのはアプリ（実際のファンクラブサイトにおける処理）が絡む要件であるため、SRE側だけでは決めかねる。
- チケット購入時のDBへの問い合わせは読み取りだけでいい。そういう時はRDSリードレプリカを使うといい。

RDSリードレプリカは読み取り専用のDBコピーであり、キャッシュと違ってプロバイダ（今回だとAWS）が非同期で複製されたDBの更新を行ってくれます。
理論上はキャッシュと同じ問題点が生じる可能性もありますが、RDSリードレプリカはAWSが更新を管理するため、アプリ側でキャッシュ無効化ロジックを実装する必要がありません。
また、チケット先行販売では「有料会員が無料会員扱いになる」ケースまたはその逆を防げれば十分であり、レプリカの同期ラグ（通常ミリ秒〜数秒）は許容できると判断して採用しました。

## 振り返り

### できなかったこと

今回は時間が足りず、セキュリティ、監視や開発環境についてまでは考えられませんでした。
もし時間があれば、以下の構成でアーキテクチャを更新しようと考えています。

#### セキュリティ
- AWS WAF：AWSの提供するクラウド型WAFのサービス。CloudFront、Application Load Balancer、API Gateway、AWS AppSyncなど複数のサービス上で動作し、SQLインジェクションやクロスサイトスクリプティングなどを防ぐ。
- AWS Shield：AWS上で動くWebアプリケーションを守るマネージドのDDoS対策サービス。
#### 監視
- Prometheus × Grafana：コンテナ環境と相性がいい。
#### 開発環境
- Terraform：AWSサービスをモジュール化し、IaC管理できる。
- ArgoCD：コンテナをGitOpsで管理できる。

### 学んだこと

メンターからのフィードバックを通じて、DBの読み書きを目的ごとにエンドポイントで分けるという手法を学びました。
無料会員から有料会員への変更（書き込み）はプライマリDBで行い、会員ランクの参照（読み取り）はリードレプリカに向けるといった使い分けです。
これにより、プライマリDBへの負荷を分散しつつ、チケット先行のような高トラフィック時でも安定した参照を実現できます。
また、AWSやGoogle Cloudを単独で使うのではなく、複数のクラウドサービスを組み合わせた方が性能やコストで有利になるケースもあると教わりました。
例えば、CloudFrontの代わりにCloudflareのCDNを活用するなど、特定のドメインに強いプロバイダを使うといった感じです。
さらに、他の学生の発表では、「このサービスを使うと速い・安い」と述べるだけでなく、具体的に何秒・いくら改善されるかを数値で示してアーキテクチャを評価しており、とても参考になりました。
加えて、SREの視点では「アプリケーション層で対応するか、インフラ層で捌くか」を状況に応じて判断する力が重要だと感じました。
コストやパフォーマンスの観点から、どの層に責任を持たせるかという設計判断は、実際の現場でも問われる場面が多そうです。
